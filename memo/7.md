# パーサの仕組み

簡易構文パーサは以下のような大枠の仕組みが考えられる。構文木を作らず、簡易構文から直接出力したいテキストに変換してしまう方式。

A. 正規表現による置換のみ
B. 1字カーソルのみ
C. 正規表現による範囲取得＋範囲を独自パース処理

上ほど簡単。でも問題もある。Markdownのフェンスなどで囲まれた領域をパースする時はB,Cでないとダメだ。Aだとフェンス内外問わず置換してしまい誤爆するから。

# 各方法の問題

Aは置換後に後続の置換をすべき箇所でないのに置換してしまいうる。

Bは範囲を特定のメタ文字で明記せねばならずパイプ省略形ルビ記法`漢字《かんじ》`のように特定の開始メタ文字がない場合に対応が困難。不可能ではないが漢字全てを開始メタ文字として判定せねばならぬため、原稿1字ずつ漢字を表す正規表現`/(?:[\p{Script=Han}々〆〇仝〻ヶヵ][\uFE00-\uFE0F\u{E0100}-\u{E01EF}]?)+/gu`で調査せねばならず負荷が高すぎる。

```javascript
const kanjiRegex = /(?:[\p{Script=Han}々〆〇仝〻ヶヵ][\uFE00-\uFE0F\u{E0100}-\u{E01EF}]?)+/gu;
const text = "一ヶ月の間、葛󠄀飾区の佐々木さんと〻同じ場所へ行った。";
console.log(text.match(kanjiRegex));
// 出力: ['一ヶ月', '間', '葛󠄀飾区', '佐々木', '〻同', '場所', '行']
```

CはAとBの間を取った方法。独自パースする領域を指定し、それぞれにパースする。なので構文の自由度が高い。代わりに異なる領域が出るたびに、例え部分的に同じ処理であろうと領域の個数だけその処理を実行することになるから負荷が高まる。

# 実装構想

1. 処理の配列
2. 正規表現の配列（`/.../gu`で結果オブジェクトを取得しつつ、それを任意文字列に置換する）
3. 正規表現の配列（ネスト構造）

## 2. 正規表現の配列

`gu`フラグのついた正規表現を生成して一括置換する。正規表現文字列を渡して、その結果を受け取る関数を使って結果文字列を返す。

```javascript
// 正規表現言語.構文定義|構文解析
const syntax = new RegLan.Syntax();
syntax.add(
  'ruby-pipe', 
  `｜(?<rb>[^｜《》\n]+)《(?<rt>[^｜《》\n]+)》`, 
  (text,syntax,groups,index,length)=>{//index,lengthはtext(原稿)中のヒット範囲位置
    return `<ruby>${groups.rb}<rt>${groups.rt}</rt></ruby>`
});
syntax.add(
  'ruby-omit', 
  `｜(?<rb>(?:[\p{Script=Han}々〆〇仝〻ヶヵ][\uFE00-\uFE0F\u{E0100}-\u{E01EF}]?)+)《(?<rt>[^｜《》\n]+)》`, 
  (text,syntax,groups,index,length)=>{//index,lengthはtext(原稿)中のヒット範囲位置
    return `<ruby>${groups.rb}<rt>${groups.rt}</rt></ruby>`
});
syntax.add(
  'em', 
  `《《(?<text>[^｜《》\n]+)》》`, 
  (text,syntax,groups,index,length)=>{//index,lengthはtext(原稿)中のヒット範囲位置
    return `<em>${groups.text}</em>`
});
syntax.add('paragraph',...);
syntax.add('heading',...);
const html = RegLan.parse(text, syntax);
```

## N. フェンス

改行コードすらテキスト内容に包含できる記法であるフェンスは正規表現で表現不能だ。

```javascript
syntax.add(
  'fence', 
  `^(?<head>[`]{3,}[^`\n])\n(?<body>.+)\n(?<foot>[`]{3,})$`, 
  `^(?<head>[`]{3,})(?<info>[^`\n])\n(?<body>([\s\S]*?))\n(?<foot>[`]{3,})$`, 

  (text,syntax,groups,index,length)=>{//index,lengthはtext(原稿)中のヒット範囲位置
    return `<pre>${groups.body}</pre>`
});
```

* 開始行と終了行の同一判定不能（3連続以上メタ文字の数が同じ数であるという制限を付与できない）
* ネスト構造内であるか否かを判定できない

上記が一番の問題だろう。

もしトップレベルにある一番外側のフェンス範囲だけを抽出できれば、その内側と外側でパースアルゴリズムを振り分けることができるのだが。

これはつまり2段階の正規表現に分割して最上位フェンスの範囲を抽出すればよい、という話になりそうだ。

* フレーム（Frame）
	* 開始行
		* フェンス（行頭で始まり、特定の字が3つ以上連続している部分）
		* ヘッダ（フェンス末尾から改行コードまでの間にある任意テキスト部分。フェンスと同じ文字列がヘッダの末尾に含まれないこと。もし含まれたらそれはインライン要素でありフレームでない）
	* 本文（開始行から終了行までの間にある任意テキスト部分。各行の冒頭から始まる文字のうち開始フェンスと同じかそれより長いフェンスが存在しないこと。同じ長さは終了行として解釈されて閉じられてしまう。より長いものは可読性向上のため包含させない。つまり親ほど長いフェンスであるべき。違反したらパースエラーとして通知すべき）
	* 終了行（開始行と同じフェンス＋EOFまたは改行であること。終了フェンスは必須。なければ構文違反エラーとして通知すべき）

フレームを抽出したら、その位置の範囲内はフレーム独自置換をし、それ以外の範囲テキストは、非フレームの置換をする。という方法にする。

```javascript
const syntax = new RegLan.Syntax('`');

// 非フレーム置換
syntax.add('ruby-pipe',...);
syntax.add('ruby-omit',...);
syntax.add('em',...);
syntax.add('paragraph',...);
syntax.add('heading',...);

// フレーム置換
syntax.add(new RegLan.FrameSyntax('`', (header,body,self)=>{//selfはこのメソッド自身（再帰用）
  return html;
}));

// パースする時はフレームからパースし、フレーム外の部分は非フレーム構文を適用する。
const html = RegLan.parse(text, syntax);
```

でもこれでも、Block要素の場合はInline要素のパースをする、みたいな部分再帰処理ができないなぁ。

もやはRegLanという名前は不適切だ。RegExpは正規表現だが、フレーム（フェンス）のパースは正規表現では不可能だ。故に独自の構文としてFrameSyntaxを用意したのだ。なんと名付けたらよいか。

糖衣構文。SugarSyntax。

> 結論から言うと、「別言語への置換や構文木（AST）への相互変換を行う仕組み」そのものを指す最も正確な言葉は、「言語（Language）」ではなく「レンズ（Lens）」または「双方向変換（Bidirectional Transformation / BX）」です。

Lenstとでもしておこうか。

```javascript
const syntax = new Lenst.Syntax();
syntax.add({
  name:`識別名`, 
  reg:`正規表現文字列`,
  replace:(text,options,groups,index,length)=>{},
  tokenize:(text,options,groups,index,length)=>{},
  lex:(text,options,token)=>{},
});
syntax.add(new Lenst.FrameSyntax('`', {
  replace:(head,body,foot)=>{},
  tokenize:(text,options,groups,index,length)=>{},
  lex:(text,options,token)=>{},
}));
const html = Lenst.replace(原稿, syntax);
const astNodes = Lenst.parse(原稿, syntax);
const 原稿 = Lenst.unparse(astNodes, syntax);
```

でもこれだとunparseはできないのでは？　原稿の構文が正規表現で定義されているため。つまりAstNodeの種別から原稿を生成するコードを別途実装せねばならない。そのロジックが存在しないためunparseができない。

ならば文字列置換構文構築者という枠組みにするほうがよいか。

* TextReplaceBuilder
* Retx

```javascript
const syn = new Retx.Syntax();
syn.add(`識別名`, `正規表現文字列`, (text,options,groups,index,length)=>{});
syn.frame.add('`', (head,body,foot,recurse)=>{});
const html = Retx.replace(原稿, syntax);
const tokens = Retx.tokenize(原稿, syntax);
```

replaceが本懐。tokenizeはオマケ。拡張構文を作りたい時にRetxを部品にできる。

## 3. 正規表現の配列（ネスト構造）

特定の要素で特定の部分再帰をする。これを定義できるような構造にしたい。さもなくば重複コードが量産されてしまう。

つまり、構文定義とそのパーサ(replace/tokenize)を持った部分パーサ的なものがあり、それを内部で使えるようにすることで重複のない実装ができるようにしたい。

```javascript
const fenceLayer = new Retx.Layer();
const blockLayer = new Retx.Layer();
const inlineLayer = new Retx.Layer();


const fenceLayer = new Retx.Layer({
    reg: [
        ['name', '正規表現', (text,options,groups,index,length)=>{}],
        ...
    ],
    frame: [
        ['`', (head,body,foot,recurse)=>{}],
        ...
    ],
});
const blockLayer = new Retx.Layer();
const inlineLayer = new Retx.Layer();



Retx.Layer.add('frame', {
    reg: [
        ['name', '正規表現', (text,options,groups,index,length)=>{}],
        ...
    ],
    frame: [
        ['`', (head,body,foot,recurse)=>{Retx.Layer.block.parse()のように呼び出せる}],
        ['`', (head,body,foot,recurse)=>{Retx.Layer.block.rubyPipe.parse()のように呼び出せる}],
        ...
    ],
});
Retx.Layer.add('block', {
  ['rubyPipe', 
  `｜(?<rb>[^｜《》\n]+)《(?<rt>[^｜《》\n]+)》`, 
  (text,syntax,groups,index,length)=>{//index,lengthはtext(原稿)中のヒット範囲位置
    return `<ruby>${groups.rb}<rt>${groups.rt}</rt></ruby>`
  });],
  ...
});
Retx.Layer.add('inline', {
    ...
});


const syn = new Retx.Syntax();
syn.add(`識別名`, `正規表現文字列`, (text,options,groups,index,length)=>{});
syn.frame.add('`', (head,body,foot,recurse)=>{});
const html = Retx.replace(原稿, syntax);
const tokens = Retx.tokenize(原稿, syntax);

```
